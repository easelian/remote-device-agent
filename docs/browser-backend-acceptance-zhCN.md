# 原生浏览器后端验收指标

状态：与[后端规约](browser-backend-contract-zhCN.md) 0.2 配套的分阶段验收计划，版本 0.2，2026-11-16。

**本文定义判定方式，不是测试报告。实施结果按具体提交、阶段和子场景另行记录；通过 D1a 不能写成 D1 或全部 BC 项目通过。**

## 1. 验收单位与判定规则

验收单位为“Agent 提交 + Server 提交（涉及 MCP 时）+ 后端实现 + 浏览器精确版本 + OS/CPU + 观察 profile + 策略组合”。不同组合不能共用一个 passed 标记。

每项记录以下结果之一：

- `passed`：在声明支持的组合实际执行并满足断言。
- `failed`：任何必要断言不成立；修复后必须针对相关场景重验。
- `unsupported_correctly_refused`：功能未提供，且在副作用发生前正确拒绝。这证明降级处理正确，不证明功能已实现。
- `not_run`：缺环境、缺实现或缺证据。不能算作通过。
- `not_applicable`：按冻结能力矩阵确实不适用，须记录依据；不能用来排除核心规约。

核心语义、授权、输入结算及资源所有权不允许豁免。可选上传、下载、AX 增强等分别计算功能覆盖率和拒绝正确性，不将两者合并成“全功能通过”。

BC 编号是长期能力范围，不是每次提交必须全部运行的清单。一项含多个阶段时，使用 `BC-xx/<stage>/<scenario>` 记录子结果；只有本阶段全部适用子场景满足才可报告该阶段通过，未实现阶段保留 not_run。D1 的参数组合是 CDP/v1 与公共端口替身，D3 才加入 BiDi/semantic_dom_v1。不能将后续阶段未实现记成 D1 回归失败，也不能用 D1 结果替代它们。

原基线的 Agent 189 项常规测试、24 项真实 Chrome 场景、5 项 Linux 沙箱测试，以及 Server 的相关回归，只能作为迁移前已有证据。新抽象必须重新经过相应测试，不能继承一个总体绿色结论。

## 2. 环境和证据要求

固定测试浏览器的可执行文件摘要、产品版本、启动参数、OS/内核、CPU 架构、CPU 配额、Rust 工具链、测试场景版本及本地策略。首次实施冻结两个浏览器的精确版本；不在此处猜测未来最低支持版本。

使用自建确定性页面与本地 HTTP/HTTPS fixture，避免第三方网站变化影响结果。页面应有明确的记录 ID、事件计数和输入日志；这些仅为合成数据，不使用真实账号或生产凭据。导航策略测试使用隔离的 DNS/地址模拟及计数服务，不请求真实云元数据地址。

保存三类证据：

1. 场景结果：操作 ID、场景 ID、预期与实际状态、合成页面的输入/请求计数。
2. 执行证据：提交/响应/控制换代顺序、EffectTicket 生命周期、事件缺口、资源计数。仅保存允许的元数据，不保存真实输入值或调试端点。
3. 环境与产物：精确提交、浏览器及平台版本、能力矩阵、测试命令、退出码、JUnit/结构化结果与必要截图。

故障注入至少覆盖提交前、入队失败、入队后未写出、已写出未响应、响应与调用者超时交错、清理期间。使用 channel/barrier、可控时钟或传输端点锁定位置；超时只作为测试挂起的外层保护，不能靠随机 sleep 猜测是否到达故障点。随机调度用于扩大覆盖，失败记录 seed 和完整操作序列。

BC-01 不以文本 grep 单独替代架构审阅。公共模块的端口和替身不得依赖协议类型；在单 crate 中运行时可以仍链接 CDP 模块，不要求为了这个测试拆 crate。D1a 的公共提交门以无协议的闭包/队列替身验证，D1b/c 再验证页面与会话端口。遇到不能表达的行为应修订规约，不能增加 `raw_command` 逃生口。

BC-02 的端口语料还须覆盖协议命令成功但脚本异常、undefined/null、非有限数、截断的嵌套对象和失效节点句柄。预期是具体的 typed error 或合法结果；脚本异常/解码失败不得成为“页面为空”的成功观察。CDP exceptionDetails 与 BiDi evaluation exception 分别喂入各自 adapter，再比较公共结果，不共用错误的原生 JSON 解析器。

BC-19 的“零错误目标输入”只覆盖可控、已定义的稳定及提交前可观察失效场景。BC-20 是必要的限制验证，不能用它为 BC-19 的失败免责，也不能要求现有浏览器协议提供其不具备的网页事务保证。

D3 输入 oracle 在执行前冻结：普通 ReplaceText 必须经过原生编辑/按键路径并产生编辑事件，最终值完整相等；允许浏览器对 key/beforeinput/input 的切分和 inputType 有已记录差异。固定 SetFormValue 的 select/日期等语料按规定的合成 input/change 验证；不得将其事件来源标为原生。D1 则保留既有 v1 断言；已知的平台修饰键缺口单列，不能用 Linux 成功推广为 macOS 成功。

## 7. 并发、事件与故障

| ID | 场景与方法 | 必须满足的结果 | 证据 |
| --- | --- | --- | --- |
| BC-24 | pause/close 与提交门交错，普通队列满，观察长时间运行 | fence 后旧代次新提交为 0；已提交工作仍可结算；控制路径不等待普通任务锁 | 提交序列、fence 时刻、队列状态 |
| BC-25 | 在第 2 节规定位置注入 timeout/disconnect/cancellation；多子命令中途失败 | 只有无副作用提交时才报 not_sent；Possible 不降级为 None；未知动作自动重放为 0；原回执可查询 | 故障位置、输入计数、回执和 EffectProgress |
| BC-26 | 已超时命令迟到成功、迟到失败、调用者已丢弃结果 | 命令槽位和输入屏障保持到结算；迟到响应不能绑定新命令，不覆盖新代次页面结果 | pending 计数、关联 ID 及回执更新 |
| BC-27 | 事件/响应交错、重复及迟到事件、critical 队列溢出、协议断帧或超长消息 | 已失效身份不复活；关键事件缺口立即禁用输入/披露并清理；坏消息不导致无界内存或裸 payload 日志 | 解析结果、状态转移、内存与输出检查 |
| BC-28 | 导航等待加载，同时暂停文档请求；DNS 决策慢；弹窗阻塞输入 | 事件、策略和控制路径仍可推进；超时有界；不能形成循环等待 | 故障调度轨迹及完成期限 |
| BC-29 | 两个 session、多个 frame/主体并发；同 operation ID 重连；错误主体查询回执/对象 | 对象、事件和回执不串线；重复操作不再次输入；权限拒绝不泄露其他主体内容 | 合成主体标记、操作计数和拒绝结果 |

先为 BC-24～29 列出状态转移和故障位置，使用确定性测试覆盖每条适用转移，生成次数不能代替覆盖。D1a 至少验证：换代先于入队、入队先于换代、队列拒绝、命令超时、调用者取消、迟到成功/失败、读取与输入屏障区分。无新增状态机时不为达到数量建立通用随机测试框架。

D1 完整验收及 D2 传输验收补充可控调度：每实现 10,000 个有界序列，每序列最多 64 步，固定种子集，并报告上述转移的实际命中次数及每步不变量。测试在内存端点上运行，不启动 10,000 次浏览器。真实浏览器的控制权、未知结果和崩溃恢复关键场景在 D1 完整验收、D3 及发布时，对各声明组合连续运行 20 次；不能以重跑至成功抵消失败。D1a 使用全部 24 场景一次和受影响的确定性故障测试，不以它冒充完整压力验收。

BC-32 是 Firefox 发布阻断项。单用户隔离测试环境中的可用原型，只能证明原型行为；不能据此宣告任意共享桌面环境都满足主体隔离。若所需隔离无法在既定部署约束下实现，保持该平台/策略组合不可用，并重新评审支持范围。

### 9.1 性能测量与放行门槛

CDP 相对回归、控制权及部署约束用于 D1 完整放行；Firefox 绝对时延和 RSS 增量暂为待基线校准的目标，在 D2 获得首批数据后、D3 输入测试前冻结。不得把未测的目标写成已有性能保证，也不能在看到失败后直接放宽断言。

同机比较使用相同 Rust release profile、浏览器二进制、字体/视口/DPR、CPU 集及内存限制。每次测量复用已打开的会话；页面在每个动作后恢复到固定状态，恢复时间单列。观察固定节点/字符上限，截图固定画面及编码参数，点击具有可计数而不导航的效果。以操作准入至结果就绪为耗时边界，至少三个交替的基线/候选批次，各预热 20 次并采集 100 个有效操作；同时保留所有拒绝和失败。报告每批 p50/p95、配对增量和环境负载。若同构建基线批次自身的波动超过门槛，结果为 not_run（测量条件不足），不能挑一个较快批次放行。

| 指标 | 测量方法 | 门槛 |
| --- | --- | --- |
| CDP 迁移后的稳态耗时 | 按上述批次方法；2 CPU/4 GiB，分别测观察、点击和截图；不同操作不混样本 | 每个批次配对的 p50 增量 ≤ max(基线的 10%, 5 ms)，p95 增量 ≤ max(基线的 15%, 10 ms) |
| 原生协议往返数量 | 在同一固定页面统计每次语义操作的命令数量及关键路径 | p95 不超过基线的 120%；新增必要校验须列出，禁止逐节点 N+1 往返代替已有批处理 |
| 控制权 fence 响应 | 普通命令队列满且事件洪峰时，从合法控制请求被公共层接纳到旧代次准入关闭；1,000 次 | p99 ≤ 100 ms；这是 fence 延迟，不是已提交浏览器输入全部结束的时间 |
| Firefox 基础体验（待校准目标） | 固定本地 fixture，页面含 5,000 DOM 节点、最多 20 frame；2 CPU/4 GiB；启动 30 次，观察/输入各 100 次 | 冷启动至 Ready p95 ≤ 10 s；单段观察 p95 ≤ 3 s；稳定控件输入确认 p95 ≤ 1 s；不包含站点业务等待 |
| 回收与内存 | 预热后 100 个正常会话循环，区分 Agent 与浏览器 RSS；记录开头及末尾各 10 次空闲样本 | 必须在现有平台关闭预算内结束或明确 CleanupPending，对象计数归零；RSS 增长 ≤ 16 MiB、新后端空闲开销 ≤ 8 MiB 暂为待校准目标 |
| 部署体积 | 同平台同 release profile 比较剥离后的 Agent 二进制和运行时依赖清单 | 二进制增量 ≤ max(基线的 15%, 2 MiB)；新增外部运行时包/驱动为 0 |

网络或浏览器本身超时的负向场景不按基础体验时延判失败，而按明确的期限、状态和所有权断言验收。性能样本不得只保留成功重试后的数据；超时和失败单独统计，任何核心正确性失败均阻止性能结论用于放行。

### 9.2 平台矩阵

首个可对比开发组合为 Linux x86_64 原生 Chromium/CDP 与 Firefox/BiDi。它用于验证抽象是否成立，不代表其他平台自动获得支持。

发布前为每个要声明支持的组合填写精确版本与实测结果：

| 组合 | 必要证据 |
| --- | --- |
| Linux x86_64 / ARM64，GNU / musl Agent | 运行的 Agent 与浏览器均为所声明架构；私有目录、sandbox、进程组、端点限制和恢复 |
| macOS x86_64 / ARM64 | 原生运行、进程归属、资料锁、主修饰键、DPR、异常退出及端点隔离 |
| Windows x86_64 / ARM64 | 原生 Job/supervisor 生命周期、ACL、资料锁、DPR、端点隔离及异常退出 |
| Chromium 品牌/发行版、Firefox stable/ESR | 各自明确的产品和精确版本；不把一个品牌或 stable 版本的成功推广到全部产品/ESR |

核心真实浏览器场景在 PR CI 执行首发组合；全部声明支持的组合在发布前执行。缺少某个原生浏览器产品时，该组合保持未验收，不用八目标交叉构建替代。可选扩展建立自己的矩阵。

### 11.1 D1a 的最小可执行证据

| 子场景 | 可控条件 | 判定 |
| --- | --- | --- |
| 提交前换代 | 同步换代后调用旧许可，enqueue 闭包记录调用次数 | 拒绝且闭包调用 0 次，操作未标记副作用 |

| 超时及迟到响应 | 已收到请求，延迟成功或错误到调用期限之后 | 调用报告 unknown；响应前 pending 保持，响应后释放；已提交标记保持 |
| 调用者取消 | 已收到请求后 abort 调用任务，再送原响应 | abort 不释放在途所有权；迟到响应只结算原命令 |
