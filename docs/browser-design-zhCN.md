# 浏览器能力设计与验收

本文是浏览器后续实现和持续回归的唯一设计入口。当前代码行为见[实现现状](browser-implementation-zhCN.md)。本文中的新工具、扩展字段、缓存和新增预算都是待实现方案，不能据此声明已经支持。BC/EX 是可持续引用的断言编号，不是迭代日志或通过记录。

## 1. 每轮迭代的维护规则

1. 实现前对照现状、源码和测试，只在本文修改仍未完成的设计、依赖、预算与验收条件；具体接口或支持范围变化先写清前置条件和拒绝边界。
2. 实现后在同一实现提交或配套提交中更新现状文档的行为、源码位置、默认值、资源上限和限制，并核对 Server schema、错误目录、Runtime 函数及使用手册的受影响内容。
3. 从本文删除已经实现的方案段落；将持续适用的断言保留为回归要求，新增代码测试成为可执行依据。部分完成时只保留剩余工作和依赖，不追加“某轮完成”小节或已完成清单。
4. 提交说明记录本轮验证范围、结果和未运行项。原始失败、JUnit、日志、截图、浏览器摘要与性能样本放在忽略的构建目录或外部证据存储；不在文档目录创建日期、阶段、对话、调研报告或验证结果文件，也不把替代文档搬入 archive。
5. 删除或改名文档时同步修复入口和引用。评审同时检查这两份文档与代码的一致性；纯文档变更核对链接、示例和断言，运行时变更执行受影响测试，不用文档措辞替代行为验证。

## 3. CDP 事件接纳回归

事件通道的当前实现与数值上限见[实现现状](browser-implementation-zhCN.md#61-cdp)。后续扩展增加事件订阅或消费者时，须维持共享许可、消费者退出和原生命令准入的边界；CDP 与 BiDi 的预算不同，不能互相替代证据。

**EX-00：CDP 事件预算与源头停止。** 用可控 pipe 固定事件消费停顿，在 256 条及 8 MiB 聚合已编码字节恰好上限、超一项时检查占用与下一输入。关键消费者尚未 recv 时，超限/缺失/退出判定已经关闭新命令准入，原生端点不能收到下一条输入；已提交命令保留 unknown 及资源所有权，迟到响应只结算原工作。覆盖多个消费者共享事件、派生任务继续持有许可、序列缺口、启动订阅顺序、第三个消费者拒绝、超大单消息、意外对象事件、弹窗和附件。记录编码字节、结构/副本占用、RSS 峰值和关闭归零；不得增加现有 2 MiB 单消息、256 条和 8 MiB 聚合上限。可执行边界见 [event_tests.rs](../src/browser/engine/cdp/wire/event_tests.rs)、[decode_tests.rs](../src/browser/engine/cdp/decode_tests.rs) 和 [submission_tests.rs](../src/browser/engine/cdp/wire/submission_tests.rs)，并持续执行真实 v1/共同语义、公开链路、fence 与性能回归。

## 4. 扩展发现与实现职责

`capabilities.browser.version` 继续为 `1`，v2 的 `selection` 继续仅包含 `version`、`observation_profile`、`backend`。扩展通过独立字段声明，不向 `selection` 添加诊断、缓存或自动回退开关。

诊断扩展的发现位置固定为 `capabilities.browser.v2.backends[].extensions.actionability` 和打开结果的 `capabilities.extensions.actionability`。字段为 `version: 1`、布尔值 `available` 和可空的 `reason`；候选不可用时沿用对应后端的构建、平台、策略或浏览器缺失原因。当前实现尚不提供这些字段，下面仅表示待实现的接口形状：

```json
{
  "extensions": {
    "actionability": {"version": 1, "available": true, "reason": null}
  }
}
```

诊断扩展仅用于显式 v2 / `semantic_dom_v1`，复用现有 v2 构建和本地策略门。Core 判断自身工具 schema 与在线 Agent 候选是否支持请求；Agent 再根据会话固定的后端、profile、扩展版本和本地策略验证。打开结果仅声明本次已启用的扩展，候选可用不能替代握手。新的内容读取仍在完成后检查披露权限和控制代次。

兼容处理固定如下：

- 不带新增参数的请求保持原结果格式；v1 不接受新增的 v2 展示参数。
- 缺扩展、未知扩展版本或不匹配的 profile 在采集页面、创建资源和输入之前拒绝，沿用适用的 `browser_feature_unsupported` 或参数错误；不猜测替代后端。
- 新客户端先读 MCP 工具 schema，再读设备与会话能力。旧 Core 不认识新工具或参数时，客户端继续使用原来的完整观察；不得把未发送的新请求改成一次隐式动作重试。
- `not_sent`、`unknown`、原错误码和错误文案继续按现有执行进展生成。新诊断正文不写入变更操作回执，不扩展数据库摘要白名单。
- 新只读操作复用现有设备权限、普通准入和计量，不因命名为“诊断”而加入免配额的后续操作列表。若需要改变计费分类，必须单独设计和验收。

新增能力沿现有所有者扩展：`selection.rs` 负责候选扩展声明，`runtime/v2.rs` 负责实际会话能力与最终披露，`semantic/page.rs` 提取纯判定并复用固定程序，adapter 补充类型化原生事实。展示缓存只归 Agent 会话所有，不持有原生节点、脚本对象或输入许可；Core 不建立第二套页面身份，也不从缓存重建已被 Agent 拒绝披露的内容。

Server 同步修改 `contracts/mcp/v1/tools-list.json`、`apps/core/src/mcp_tools.rs`、`mcp.rs`、`browser.rs` 及公开契约测试。新只读工具复用认证、普通准入、计量和最终披露，不因名称为“诊断”加入 `TASK_FOLLOW_UPS`。页面正文、诊断和差分不写入变更回执或新增持久缓存表；若另有 Runtime 函数变更，仍按二进制/函数配套规则验收与回退。

## 5. 只读可操作性诊断

### 5.1 接口与结果

现有 `Failure` 只有错误码和执行状态，Core 再映射固定文案。首版采用独立的 `browser_inspect`，不让诊断正文穿过所有错误和回执路径。工具检查一个现有 ref 对指定动作种类的当前前置条件，不接收脚本、选择器、坐标、文件路径或实际输入文本。

`browser_inspect` 的参数固定如下；该工具尚未实现，示例不能发送给当前版本。`device_id`、`session_id`、`control_epoch`、`ref` 和 `action_kind` 必填；可选 `tab_id` 沿用当前会话的活动 tab 规则。引用必须是非空字符串且不超过 128 个 UTF-8 字节，其余身份字段沿用既有边界，未知字段拒绝。

```json
{
  "device_id": "test",
  "session_id": "session-from-open",
  "control_epoch": 1,
  "ref": "ref-from-latest-observation",
  "action_kind": "click"
}
```

结果固定包含 `diagnostic_version: 1`、`session_id`、`tab_id`、`control_epoch`、既有 `selection`、`action_kind`、`status`、`reasons`、`conditions` 和 `content_trust: untrusted_page`。`action_kind` 仅接受 `click`、`press`、`fill`、`check`、`select`、`attach_file`，并在结果中原样返回。输入值、按键参数、上传授权和幂等无操作判断仍由真实动作完成；`attach_file` 诊断只检查控件类型、可操作性和主文档限制，不查阅或消耗文件授权。

首版只检查当前仍有效的动作 ref，不为所有观察行另建诊断引用表。现有 `Facts::eligible` 不给禁用或隐藏目标签发 ref；这类状态由完整观察中的已有事实说明。目标在观察后变为禁用、隐藏或记录已变化时，检查继续返回既有 stale 错误，不能为了给出详细原因而放宽指纹校验。没有 ref 的节点不能通过名称、索引或选择器送入此工具。

| status | 含义 |
| --- | --- |
| `ready_now` | 采样时满足所检查的前置条件；不保证稍后的输入可执行或业务成功 |
| `needs_scroll` | 目标在当前视口外；真实动作可能按现有流程滚动，诊断本身不滚动 |
| `blocked` | 有效引用下已确定只读、遮挡、敏感输入限制或动作类型不适用 |
| `indeterminate` | 无法在期限或现有几何保证内完成判断；不能当作可操作 |

原因枚举固定为 `read_only`、`covered`、`outside_viewport`、`unstable_geometry`、`unsupported_geometry`、`sensitive_target`、`unsupported_action`，去重后最多 8 项。原因按请求的动作种类判断；只读文本框仍可能接受 click，不能把 `read_only` 一概视为所有动作的拒绝原因。

`conditions` 固定包含布尔值 `read_only`、`sensitive`、`editable`，以及可空布尔值 `in_view`、`hit`、`stable`。后面三项未采集或无法证明时为 `null`，不能用 `false` 伪装缺少的证据；有两次采样时报告最后一次位置/命中事实及两次是否稳定。结果不返回页面文本、值、DOM 路径、坐标或原生 ID。过期引用、文档变化、错误主体和控制权变化仍走现有错误路径，不能借诊断重新匹配目标。

### 5.2 公共实现与副作用边界

把 `semantic/page.rs` 中可操作性判定提取成接受 `Facts`、`Geometry` 和动作种类的纯函数。动作与诊断复用判定规则，但保留各自采集流程：动作可以在授权后滚动并再次检查；诊断只执行身份刷新、固定 Inspect、只读几何/命中检查和必要的二次稳定性采样。

诊断不得调用 `perform` 的完整流程，不执行 Scroll、Focus、输入、表单设置或上传授权消耗。检查不续期 ref/cursor，不签发新 ref，不把 `ready_now` 保存成下一动作的授权令牌。每个真实动作继续独立检查文档、记录、控制代次及提交门。

诊断的绝对 deadline 在 Agent 接纳该调用时固定为调用剩余期限与 1 秒的较小值，包含普通锁等待、身份刷新、几何采集和两次采样之间的 50 ms 间隔。原生命令继续使用这个 deadline，不重新延长。已确定类型不支持、只读、敏感限制、视口外或遮挡时可提前返回；准备返回 `ready_now` 时必须完成第二次身份与几何校验。

包括会话标识、控制代次和 selection 的 Agent 诊断正文，UTF-8 JSON 编码后不得超过 4 KiB；该上限不包含既有 MCP 传输封装，传输自身上限继续生效。检查不创建第二套节点表或缓存。取消、超时和迟到响应沿现有租约结算；人工接管能立即关闭旧代次准入，不等待诊断持有普通锁。仅靠错误字符串分类不满足此阶段要求。

### 5.3 验收

为每个场景同时记录诊断结果、调用前后页面状态、原生命令种类、输入/导航/网络计数、控制代次及资源计数。CDP、BiDi 和 Fake 采用同一原因与状态 oracle；原生协议细节单独记录，不按后端忽略公共差异。

| ID | 场景 | 必须满足的断言 |
| --- | --- | --- |
| EX-01 | 稳定可见控件、禁用、只读、隐藏、遮挡、错误动作种类、敏感输入 | 有效 ref 的 status/reason 与冻结语料一致；禁用/隐藏目标保持无动作 ref，观察后失去资格仍返回既有 stale 错误；不返回敏感值、DOM 路径或原生 ID，不改变旧错误目录 |
| EX-02 | 目标在视口外、嵌套 frame、移动布局、旋转/透视 | 只读检查不滚动、不聚焦；不能证明的几何为 indeterminate/明确拒绝，不能误报 ready_now |
| EX-03 | 旧 ref、同名节点替换、记录变化、同 URL reload、BFCache、realm/frame 替换 | 旧身份按现有错误拒绝；没有按名称或选择器重匹配，也不签发替代 ref |
| EX-04 | 提交前后人工接管、调用取消、期限到达、迟到原生响应 | 控制 fence 可推进；结果不能越过披露边界；原生命令和租约到真正结算才释放 |
| EX-05 | 连续检查与随后真实动作 | 检查不续期引用、不产生输入/滚动/导航/表单事件、不消耗上传授权；真实动作仍重新校验并仅按既有流程提交 |
| EX-06 | 结果、原因数和期限恰好达到上限及超一项 | 受限结果或明确拒绝；没有无界等待、额外扫描或占用人工控制通路 |

`ready_now` 只对已检查前置条件负责。诊断后主动改变页面，再发真实动作，必须由动作自身发现变化；这验证诊断不会成为绕过动作校验的许可。参数值合法性、上传一次性授权和站点业务结果另由原动作场景验证。

拟新增 Agent `src/browser/semantic/tests/diagnostics.rs`，覆盖纯判定和可控时序；在既有双后端原生测试中复用同一语料。拟新增 Server `tests/core/test_browser_diagnostics.py`，从公开 MCP 验证主体、能力、计量、错误及人工 fence。新增场景完成前不改变已有套件的预期数量或断言。

## 6. 按实际能力提供指引

保留初始化阶段的简短通用说明。设备相关示例通过拟议的 `browser_guidance` 读取，参数仅包含 `device_id`、可选 `session_id` 和一个封闭的 `topic`，例如 `open`、`observe`、`recover`、`handoff`、`files`。一次返回一个主题。

Core 从已认证设备连接与本次会话能力选择随 Server 构建发布的静态模板，返回指引版本、模板内容摘要、适用的 schema/扩展版本和前置条件。不依据版本号字符串推测能力，不把一个设备的指引放进所有设备共用的初始化说明，不从网页或外部 URL 动态加载操作指令。

示例须经过工具 schema 校验，并在对应 v1、v2/CDP、v2/BiDi 组合实际执行。恢复示例先查询原操作/会话，不自动重放；人工交接示例包含明确披露和重新观察；文件示例使用现有人工授权，不包含设备路径。旧设备得到可执行的 v1 示例，未知扩展不能出现在示例中。

指引读取不采集页面正文、不创建浏览器会话、不改变默认后端。若 Agent 重连、会话关闭或能力改变，先前的指引只作为说明，下一请求仍按当前能力独立校验。

## 7. 可选增量观察

### 7.1 为什么不能直接比较现有 JSON

当前 `runtime/v2.rs::observe` 每次都会清空并重建公开 `ref`、`frame_id` 和游标映射。页面内容相同，新的结果也会包含不同的不透明标识。直接缓存整个结果会产生大量无意义差分；为了得到 `unchanged` 而保留旧 ref，又会改变已冻结的引用寿命。

首版增量观察作为 `browser_observe` 的显式展示方式。省略 `presentation` 时，参数和结果完全沿用当前格式。拟议参数为：

```json
{
  "presentation": {
    "version": 1,
    "mode": "delta",
    "base_revision": "opaque-revision-from-last-received-result"
  }
}
```

首次请求可以省略 `base_revision`，得到该展示方式的 `full` 结果。`presentation` 与 `cursor` 不能同时提供；需要续页时沿用普通完整观察。此参数需要 Core 工具 schema、Agent 扩展和接收端重建能力同时就绪。

### 7.2 投影格式与引用更新

每次调用仍执行真实观察、身份校验和现有引用替换。结果分成三部分：

1. 内容投影：有序节点及完整 canonical 字段、记录材料、页面内容和覆盖信息。移除动作 ref、公开 frame_id、游标及其他每次签发的标识；用展示用 frame 槽关联节点。
2. 当前绑定：本次所有可执行节点的 `node_index → ref`、展示 frame 槽到本次 `frame_id` 的完整映射，以及当前会话、tab 和控制代次。绑定每次全部更新；无 ref 的节点明确为空。
3. 版本封装：`kind: full | delta | unchanged`、不透明 `revision`、需要时的 `base_revision`、本会话单调递增的观察序号、结果节点数和固定的 `content_trust: untrusted_page`。观察序号按最多 20 位十进制字符串传输，溢出明确拒绝，不环绕复用。

`unchanged` 仅表示内容投影相同，仍返回新的完整绑定。展示索引和 frame 槽不能传给 `browser_act` 或当作 `within`；客户端必须使用当前绑定中的新 ID。不得按 role/name、文本或位置重新激活旧 ref。

首版采用有界数组 splice：以共同前缀和后缀确定一段替换区，逐行保留所有 canonical 字段。页面元数据变化完整替换对应小对象。节点插入、删除、排序、文本、checked/value、记录结构及名称质量变化都必须能精确重建。无需实现通用 JSON Patch 解释器或不受限的最短编辑距离算法。

### 7.3 缓存、失效与拒绝

缓存归 Agent 会话所有，键包含认证主体、Agent 实例/会话、后端、profile、tab、完整 frame/document/realm 身份集合、控制代次、查询条件以及节点/字符预算。`within` 使用验证后的内部 Context 作为查询范围，不把每次重新签发的公开 frame_id 当成稳定键。身份使用内部已验证类型，不接受调用者提供的原生 ID。URL 相同不能证明文档相同。

仅当扫描完成、没有续页、没有读取中变化及资源截断时建立基线。profile 固定声明的 closed shadow、canvas 和浏览器 UI 范围限制继续随结果保留；它们不等于支持完整浏览器内容。分页、动态页面或受限观察返回新鲜 `full`，不偷偷继续扫描到完整，也不以删掉 coverage 获得可缓存结果。

新文档、同 URL reload、BFCache、realm/frame 替换、控制权换代、人工接管、关闭、失联、重启、策略改变、查询改变和 TTL 到期均使基线失效。控制门同步使缓存不可访问；有界回收不阻塞人工 fence。展示缓存不延长任何原生租约。

缺基线、版本不匹配、被淘汰或差分无收益时，允许在同一次已授权观察中返回 `full`。权限失败、暂停、失联和身份无法证明时返回原错误，不能以“回退到 full”绕过拒绝。未知 revision 在当前会话内按未命中处理，不查询其他主体缓存，不透露命中关系。

响应丢失不等于客户端接受了 revision。客户端每次携带自己最后成功应用的版本；服务端不假定交付成功。并发调用、乱序响应和过期 epoch 必须由接收端拒绝原子替换，必要时重新请求完整结果。缓存只能在本次最终披露检查成功后成为可用版本，迟到结果不能重新插入已失效代次。

### 7.4 接收端与收益条件

增量输出默认关闭。普通 MCP 客户端继续接收完整观察；先实现一个可验证的接收端 reducer，按 base/revision、会话/控制代次和观察序号校验，检查 splice 范围及结果节点数，再原子替换全部引用和 frame 绑定。模型对历史文本的记忆不能代替这一步。首版不增加跨语言 canonical JSON 散列协议；以同一次采集生成的完整结果作为测试 oracle，逐字段比较重建结果。实际 AI 宿主或受控适配器无法保留并验证基线时，该客户端不启用 delta。

比较收益时计入完整 MCP 响应，包括绑定、元数据和可能同时存在的文本/结构化内容。只比较删掉 ref 后的页面文本会夸大收益。原生观察和身份检查仍执行，因此输出字节减少不代表原生命令或观察时延减少。

### 7.5 正确性与失效矩阵

测试从同一次已授权采集生成完整 oracle 和增量结果，避免用第二次观察的随机 ref 或页面变化掩盖差异。reducer 重建后逐字段比较内容、顺序、覆盖信息、当前 ref/frame 绑定及页元数据；不能只比较 role/name 或文本长度。

| ID | 场景 | 必须满足的断言 |
| --- | --- | --- |
| EX-11 | 初次读取、静态页、单点变化、增删/排序、表单状态、记录结构、名称质量、Unicode | full/delta/unchanged 重建与完整 oracle 一致，零丢失、零额外节点；changed/coverage 保持真实含义 |
| EX-12 | 内容相同但 ref/frame_id 更新；节点从可执行变为不可执行 | unchanged 仍带全部新绑定；旧 ref/frame_id 被拒绝；删除的绑定不残留；展示索引不能执行动作 |
| EX-13 | 同 URL reload、BFCache、realm/frame 替换、查询/范围/预算变化、控制权与策略变化 | 基线失效；授权仍有效时返回新鲜 full，授权无效时原错误；不靠 URL 相等复用 |
| EX-14 | next_cursor、扫描截断、读取中变化、记录资源限制、超缓存大小 | 不建立不完整基线；不隐式继续扫描；原观察预算与拒绝路径不变 |
| EX-15 | 错误/缺失/淘汰/到期基线、其他主体 revision、响应丢失、请求取消、乱序 full/delta、序号耗尽 | 不跨主体查找；受限 full 或明确拒绝；客户端拒绝旧序号/错误 base；失效代次不能被迟到结果重新发布 |
| EX-16 | 并发接管、关闭、失联、恢复后观察 | 内容缓存不可绕过披露；缓存不包含原生对象或输入许可；未知动作继续按原回执处理 |
| EX-17 | 每个缓存/索引/字节上限及超一项；10,000 次观察替换/淘汰/失效 | 实际占用有界；close 后缓存计数归零；普通/释放槽及原生对象预算不变；失败清理不伪造归零 |
| EX-18 | 不支持 reducer 的客户端、MCP 文本与结构化双输出、真实宿主重连 | 默认完整观察；启用增量的接收端能确定性重建并替换全部绑定；重连后重新建立基线；实际展示内容符合当前结果 |

EX-11 的公共 oracle 不接受按 backend kind 的忽略规则。至少覆盖空结果、一个节点、默认 200 项、上限 1,000 项、多个 frame、NBSP/组合字符/非 BMP、可变值和敏感字段。敏感值必须在投影与缓存之前被排除，不能只在最终显示时遮盖。

### 7.6 输出收益与原性能门槛

在实现前固定收益语料：至少 20 个确定性序列，覆盖表单、表格/列表、混合文本、Unicode 和多 frame；每序列先建立一次完整基线，再执行 20 次更新。可缓存的稀疏变化组每次变化不超过 5% 的节点，另设大变化、不可缓存和频繁失效组。所有组都保留原始结果，不事后挑选高收益页面。

| 指标 | 判定 |
| --- | --- |
| 重建正确性 | 同次完整 oracle 与 reducer 结果逐字段一致；任何差异均阻断放行 |
| 单次选择 | 输出 delta/unchanged 时，完整响应字节数 ≤ 同次 full 的 70%；否则 full |
| 可缓存稀疏组总收益 | 计入首次 full、新绑定、元数据及 MCP 双输出后，总字节数 ≤ 同组始终 full 的 70%；防止“始终返回 full”获得空洞通过 |
| 大变化/失效组 | 正确返回 full/拒绝，无额外页面输入或无限重采集；报告 full 比例和原因，不混入稀疏组提高或稀释收益 |
| 原生开销 | 记录命令数量、观察 p50/p95、缓存构造/比较时间；不得通过省略观察或身份检查获取收益 |
| 模型上下文 | 有确定 tokenizer/客户端时另存版本与 token 数；没有时只报告字节，不把字节比例称作 token 节省比例 |

增量观察还须通过第 11 节的原有性能、命令数量、fence、RSS 和体积门槛；不能用输出收益抵消正确性或资源回归。

原四组 RSS 测量继续完整执行。增量观察另固定“缓存关闭/开启”的对照，覆盖缓存满载、反复失效、并发会话和 100 次关闭循环，记录序列化字节、索引容量、构造副本、实际 RSS/PSS；不能用未填满缓存的 RSS 代替容量验收。新对照的 fixture、参数和摘要在首个样本前固定，不混入原协议的四组样本。

拟新增 Agent `src/browser/semantic/tests/presentation.rs` 和 Server `tests/core/test_browser_observation_delta.py`，并提供接收端 reducer 的共用语料。若没有能运行 reducer 的真实客户端/受控适配器，EX-18 保持 `not_run`，不向该客户端启用增量。

## 8. 新增预算草案

单次诊断的一个 ref、8 项原因、4 KiB 正文和 1 秒总期限已作为第 5 节的接口契约固定；其余能力仍使用下表中的初始设计预算，须在各自实现前的契约提交中固定。新增预算不替换既有消息、引用、命令、句柄、性能及 RSS 门槛；实现同时满足两组限制。未达到收益目标时不公开优化能力，不在看到结果后放宽目标。

| 对象 | 预算 | 超限处理 |
| --- | --- | --- |
| 单次诊断 | 一个 ref；最多 8 个原因；Agent 诊断正文 UTF-8 JSON ≤ 4 KiB；总期限不超过调用剩余期限与 1 秒的较小值 | 不循环等待；检查不足返回 indeterminate 或现有期限错误，不输入 |
| 单次指引 | 一个主题；正文 UTF-8 JSON ≤ 16 KiB | 返回受限主题或明确拒绝；不隐式拉取后续内容 |
| 单个内容基线 | 序列化投影 ≤ 256 KiB，节点/字符上限仍为现值 | 不建立基线，返回允许的完整观察；完整输出仍受现有 RPC/MCP 上限约束 |
| 缓存总量 | 每会话最多 2 个 revision；每 Agent 已存投影合计 ≤ 1 MiB；单会话新增构造暂存 ≤ 512 KiB；全 Agent 缓存节点索引 ≤ 4,000 项、frame 索引 ≤ 128 项 | 有界淘汰旧版本，缺失时 full；使用序列化字节和边界索引，不长期保留另一份解码对象树；同时核对实际分配与 RSS |
| 缓存寿命 | 最长 60 秒，且不超过已有 ref/cursor 和会话寿命；不因命中无限续期 | 到期失效；缓存不落盘、不写日志或回执 |
| 差分计算 | 单次 O(N) 前后缀比较，N 受当前 1,000 项上限约束；最多一段节点 splice | 不引入无界任务、递归 patch 或逐节点原生查询 |
| 输出选择 | 含新绑定的 delta/unchanged 完整响应必须 ≤ 同次 full 响应的 70% | 返回 full；完全相同内容也可能因绑定较大而不适合增量 |

## 9. 独立检查扩展

原生 AX 采用独立输出 profile 或能力，不覆盖 `semantic_dom_v1` 的名称、角色和引用资格，首版不从 AX 节点签发动作引用。控制台、网络和 trace 各自定义读取权限、脱敏、保留时长、事件数量、事件字节、完整消息大小及停止流程。

| 分段 | 实现方式草案 | 首版交付边界 |
| --- | --- | --- |
| 原生 AX 检查 | 在 adapter 增加封闭的只读 AX 端口，公共层输出独立的版本化检查结果；不复用 canonical ref | 仅提供目标浏览器已证明支持的字段，节点数/深度/字节均有界；不能声明两个引擎的原生 AX 完全等价 |
| 控制台与网络摘要 | 会话内显式开始/停止的诊断订阅；关键生命周期事件和可丢失诊断记录分开限额 | 默认只输出有界级别/计数、来源 origin、状态与时序，不输出请求/响应正文、凭据、URL 查询串或任意对象展开；丢失以 gap/dropped_count 明示 |
| 性能 trace | 有界采集任务与受限原生流，停止后生成私有诊断制品 | 不把完整 trace 内联给模型；人工交付、保留及显式删除单独定义。现有附件目录只接收受约束 HTTP attachment，新增诊断制品需要独立类型及旧版读取/回退规则 |

这些分段先提交具体 schema、单次/总量/时间预算和原生能力证据，再实现 adapter 和公开入口。诊断队列溢出可以在契约允许时丢记录并报告缺口；关键身份、导航或控制事件丢失仍必须停止，不能用同一“允许丢失”策略处理。网络观察不能改变已有导航拦截/附件流的决定，也不能为了读取正文重发请求。React 等特定应用检查按实际需求另行设计，不纳入基础后端保证。

当前 CDP 不订阅未使用的 Runtime console/exception/inspect 事件，并拒绝意外对象所有权。增加订阅会直接改变这一资源边界：必须证明事件携带的对象如何纳入现有租约上限、如何有界释放，以及容量不足时如何停止。不能直接增加无界事件 tap、丢弃对象或在超时后提前扣减占用。无法在既定预算内完成的订阅保持不可用。

扩展仍只提供经过设计的操作，不开放任意脚本、CDP/BiDi 方法或调试端点。网络正文、Cookie、Authorization、trace 和堆快照的内容范围须独立评审；它们不能因页面可被观察就自动取得披露权限。

## 10. 持续回归要求

以下保留 BC-01～40 的行为断言。它们用于当前能力和后续修改的持续回归，不记录过去迁移阶段；适用范围按 v1、v2/CDP、v2/BiDi 和实际声明组合分别报告。新功能只增加适用场景，不能删掉旧断言、静默忽略失败或放宽冻结门槛。CDP 的 EX-00 边界单独验证，不能用其他 BC 结果替代。

### 10.1 判定、环境与证据

每次记录独立的组合：Agent 与 Server 源码提交、干净工作树、构建选项、编译器/release profile、二进制 SHA-256、浏览器产品/版本/摘要、OS/CPU、观察 profile、本地策略、扩展版本及客户端版本。复用未改动的服务二进制时，记录其源码来源，并证明受影响的运行时代码与候选一致。切换候选、浏览器、构建选项或协议参数后建立新记录，不拼接旧样本。

判定使用 `passed`、`failed`、`unsupported_correctly_refused`、`not_run`、`not_applicable`。缺环境、跳过或没有执行到预期拒绝点都不能记为通过。必要用例的 JUnit 必须与事先收集的 ID 一一对应，失败、错误和跳过均为零。预期的拒绝是带断言的通过用例，报告中另列拒绝的功能及边界。

不同证据分别回答不同问题：

| 证据 | 可以证明 | 不能替代 |
| --- | --- | --- |
| Fake 与可控 pipe/WebSocket | 状态转移、取消、乱序、容量和所有权 | 浏览器实际执行 |
| 原生 Agent 场景 | 对固定浏览器的观察、输入、身份和进程行为 | Core/MCP 的认证、计量和结果披露 |
| 隔离 Server/MCP 场景 | 从公开工具到真实 Agent、浏览器及人工页面的路径 | 真实 AI 宿主的渲染、缓存与工具选择 |
| 原生平台运行 | 该 OS/CPU 的真实操作和隔离 | 其他平台、浏览器品牌或版本 |
| 八目标构建 CI | 声明目标的构建及相应检查 | 八种原生浏览器运行结果 |

固定测试浏览器的可执行文件摘要、产品版本、启动参数、OS/内核、CPU 架构、CPU 配额、Rust 工具链、测试场景版本及本地策略。首次实施冻结两个浏览器的精确版本；不在此处猜测未来最低支持版本。

使用自建确定性页面与本地 HTTP/HTTPS fixture，避免第三方网站变化影响结果。页面应有明确的记录 ID、事件计数和输入日志；这些仅为合成数据，不使用真实账号或生产凭据。导航策略测试使用隔离的 DNS/地址模拟及计数服务，不请求真实云元数据地址。

保存三类证据：

1. 场景结果：操作 ID、场景 ID、预期与实际状态、合成页面的输入/请求计数。
2. 执行证据：提交/响应/控制换代顺序、EffectTicket 生命周期、事件缺口、资源计数。仅保存允许的元数据，不保存真实输入值或调试端点。

### 11.1 性能测量与放行门槛

CDP 相对回归、控制权及部署约束用于完整验收。下表的 Firefox 绝对时延和 RSS 门槛适用于已校准的首发 Linux x86_64 GNU 组合；其他 OS、CPU、浏览器产品及版本组合须独立验证。不得把未测组合写成已有性能保证，也不能在看到失败后直接放宽断言。

同机比较使用相同 Rust release profile、浏览器二进制、字体/视口/DPR、CPU 集及内存限制。每次测量复用已打开的会话；页面在每个动作后恢复到固定状态，恢复时间单列。观察固定节点/字符上限，截图固定画面及编码参数，点击具有可计数而不导航的效果。以操作准入至结果就绪为耗时边界，至少三个交替的基线/候选批次，各预热 20 次并采集 100 个有效操作；同时保留所有拒绝和失败。报告每批 p50/p95、配对增量和环境负载。若同构建基线批次自身的波动超过门槛，结果为 not_run（测量条件不足），不能挑一个较快批次放行。

既定 CDP 对照基线为 `06e43b18763292a89fe79f2df1992e4053225ff2`，仅向其测试构建注入同一套计数器和 fixture，不修改基线生产行为。原始样本、构建摘要与所用基线一并固定；后续比较若另设基线，须在采样前明确变更目的，不能替换一次失败比较的基线或拼接不同条件的样本。统计入口为 `scripts/browser-d1-report.py EVIDENCE_DIR`。

| 指标 | 测量方法 | 门槛 |
| --- | --- | --- |
| CDP 候选的稳态耗时 | 按上述批次方法；2 CPU/4 GiB，分别测观察、点击和截图；不同操作不混样本 | 每个批次配对的 p50 增量 ≤ max(基线的 10%, 5 ms)，p95 增量 ≤ max(基线的 15%, 10 ms) |
| 原生协议往返数量 | 在同一固定页面统计每次语义操作的命令数量及关键路径 | p95 不超过基线的 120%；新增必要校验须列出，禁止逐节点 N+1 往返代替已有批处理 |
| 控制权 fence 响应 | 普通命令队列满且事件洪峰时，从合法控制请求被公共层接纳到旧代次准入关闭；1,000 次 | p99 ≤ 100 ms；这是 fence 延迟，不是已提交浏览器输入全部结束的时间 |
| Firefox 基础体验 | 固定本地 fixture，页面含 5,000 DOM 节点、最多 20 frame；2 CPU/4 GiB；启动 30 次，观察/输入各 100 次 | 冷启动至 Ready p95 ≤ 10 s；单段观察 p95 ≤ 3 s；稳定控件输入确认 p95 ≤ 1 s；不包含站点业务等待 |
| 回收与内存 | 预热后 100 个正常会话循环，区分 Agent 与浏览器 RSS；记录开头及末尾各 10 次空闲样本 | 必须在现有平台关闭预算内结束或明确 CleanupPending，对象计数归零；Agent 与浏览器 RSS 增长各 ≤ 16 MiB，新后端空闲开销 ≤ 8 MiB |
| 部署体积 | 同平台同 release profile 比较剥离后的 Agent 二进制和运行时依赖清单 | 二进制增量 ≤ max(基线的 15%, 2 MiB)；新增外部运行时包/驱动为 0 |

网络或浏览器本身超时的负向场景不按基础体验时延判失败，而按明确的期限、状态和所有权断言验收。性能样本不得只保留成功重试后的数据；超时和失败单独统计，任何核心正确性失败均阻止性能结论用于放行。

RSS 校准使用同一 release Agent，依次执行 v1 前基线、CDP/v2、BiDi/v2、v1 后基线。各组先预热 20 次会话，再执行 100 次测量会话。固定页面包含分布在 20 个 frame 中的 5,000 个空 DOM 元素和原生控件；每次打开后等待 frame 就绪，按 200 节点、20,000 字符观察，采集空闲进程树，再关闭并核对清理。测量协议、产物摘要、两个 CPU 的编号及 cgroup 限制在首个样本前固定。其他压力任务先于 RSS 测量完成。

Agent RSS 增长取预热后首、末各 10 次已关闭会话的空闲样本中位数之差，采样间隔为 500 ms，使用原有 16 MiB 目标。浏览器单独比较前、后各 10 次已打开会话的进程树 RSS 中位数；每次成功关闭后，其所属进程数及 RSS 必须归零。Agent 主进程、受管 helper 和浏览器分别记录；多个进程的 RSS 求和会重复计算共享页，能够读取时另存 PSS。新后端空闲开销取 v2 首、末空闲中位数相对两个 v1 基线的最大正差，使用原有 8 MiB 目标。两个 v1 预热后空闲基线相差超过 8 MiB 时，记为测量条件不足。所有样本、峰值和失败均保留，不用对象计数代替内存测量。

公开预算测试与原生传输测试分别记录拒绝位置。Server 的 `test_browser_v2_budgets.py` 覆盖分页、50,000 项遍历待处理队列、截图压缩率、资料与文件容量；`test_browser_v2_stress.py` 覆盖公开异常恢复及交接重复；`test_browser_v2_rss.py` 与冻结的 `browser-rss-protocol.json` 执行上述内存测量。`scripts/summarize_browser_rss.py` 从四组完整原始样本重新计算增长、基线漂移和后端空闲开销，缺样或门槛未通过时返回非零退出码。协议层使用真实 pipe/WebSocket 端点填满命令、完整 JSON 和事件字节预算，并保留固定种子序列及控制权 fence 样本。节点与字符预算同时生效时，报告实际首先触发的预算，不能把“接受 1,000 节点参数”写成“实际保留了 1,000 个引用”。

### 11.2 原生句柄与清理

实际对象、流、pending、释放槽和 BiDi root handle 上限以[实现现状](browser-implementation-zhCN.md)及代码常量为基准，不再维护第二份数值表。精确边界测试同时覆盖已返回租约和待决创建预留，各分类不能借用额度。

验收必须同时覆盖对象与流的精确边界、pending 预留、错误返回、释放失败、迟到响应、取消、同组并发响应、不同 session 的同名句柄，以及普通 32 槽满时的清理路径。Agent 的 `cdp::wire::lease_tests` 和 `bidi::wire::tests::leases` 用可控 pipe/WebSocket 验证这些时序；`native_object_lease_boundary_and_unsubscribed_runtime_events` 使用真实 Chrome 验证 256 个对象、超额拒绝、异常对象回收和 console 事件边界。保留真实 v1 扫描、并发下载、CDP/BiDi 共同语义的原始峰值，并在最终 release 构建重跑 v1 原生回归。预算冻结不代表尚未运行的平台和 Server CI 已通过。

## 12. 跨版本、提交与回退

| Core / Agent / 客户端 | 期望 |
| --- | --- |
| 新 Core / 新 Agent / 旧客户端 | 无新增参数时保持旧格式、默认后端、文案和回执；额外工具不改变旧调用 |
| 新 Core / 旧 Agent / 新客户端 | 工具和设备能力联合判断；不支持的扩展在页面工作前拒绝，原有完整观察仍可用 |
| 旧 Core / 新 Agent / 新客户端 | 先按旧工具 schema 使用已支持请求；未知新工具/参数的拒绝边界单列，不能假设旧 Core 会转发 |
| 新 Core / 新 Agent / 扩展关闭或版本未知 | 未声明的扩展不可执行；不自动更换 profile/后端；旧路径继续通过 |

实现按可独立审查和回退的职责提交：事件预算与准入；扩展 schema/纯判定；双后端采集；Core/MCP 接入；指引模板；内容投影与缓存；客户端重建；收益及完整回归。每段执行受影响验证，待完整验收后再声明支持，不新建分段文档。

诊断与增量缓存不改变磁盘资料格式，也不扩展变更回执摘要。关闭扩展后客户端丢弃展示基线、重新发现能力并完整观察；已经提交的动作继续结算，不能因关闭扩展而重放。涉及 Core 函数契约的变化继续使用现状文档中的程序/数据库配套回退步骤。

## 13. 测试执行入口与失败处理

先执行契约/纯函数与可控传输测试，再执行两个真实浏览器的受影响场景，最后执行完整本地 Server/MCP、重复恢复、独立性能比较和 RSS。只改文档时验证引用、结构和示例；不把规划中的新用例伪报成已运行，也不为文档改动启动整套原生压力测试。

现有 Server 仓库入口为 `scripts/run_browser_acceptance.py`。以下命令执行已有测试组，不包含尚未实现的扩展用例。先准备专用 PostgreSQL 和最小权限测试配置，配置文件包含实际的 `RDH_TEST_*` 可执行路径、Node、authority probe、浏览器和旧版本兼容产物；不得指向生产数据库。缺项造成 skip 时必须补齐环境，不能删掉用例。

原生场景使用 `RDH_TEST_CLUSTER_AGENT`、`RDH_TEST_BROWSER_EXECUTABLE`、`RDH_TEST_FIREFOX_EXECUTABLE`；兼容场景另需 `RDH_TEST_OLD_AGENT`、`RDH_TEST_DEFAULT_AGENT`、`RDH_TEST_OLD_CORE`、`RDH_TEST_OLD_MIGRATE`。新旧源码使用不同 Cargo target 目录。公开恢复场景对每个后端执行 100 次原生所有者丢失、20 次 Agent 丢失和 20 次人工交接，保持独立会话与持久资料断言；测试账户额度由一次性夹具配置，不改变产品计量。

在 Server 仓库根目录、已配置本项目测试依赖的 Python 环境中执行；`python3` 必须指向含 pytest 及本仓库测试依赖的解释器。先将两个变量替换为私有环境 JSON 的实际绝对路径和一个尚不存在的证据目录：

```sh
set -eu
RDH_ACCEPT_ENV=/private/fixture-environment.json
RDH_ACCEPT_OUT=/private/browser-acceptance-new
test -f "$RDH_ACCEPT_ENV"
test ! -e "$RDH_ACCEPT_OUT"
mkdir -m 700 "$RDH_ACCEPT_OUT"
for phase in contracts v1 v2 budgets recovery linux-tls; do
  python3 scripts/run_browser_acceptance.py --phase "$phase" \
    --env-json "$RDH_ACCEPT_ENV" --output "$RDH_ACCEPT_OUT/$phase"
done
```

`linux-tls` 要求配置中明确的 `RDH_TEST_BROWSER_LAN_HOST`。RSS 另在冻结协议规定的两 CPU、2 CPU 配额、4 GiB、无 swap 的 cgroup 中执行；先固定可用 CPU 编号并同步到协议，不能照抄另一台主机的编号。以下是已进入正确 cgroup 后的现有命令，路径仍需替换：

```sh
python3 scripts/run_browser_acceptance.py --phase rss \
  --env-json /private/fixture-environment.json \
  --output /private/browser-acceptance-new/rss \
  --rss-protocol /private/frozen-browser-rss-protocol.json
```

期望每阶段生成 `acceptance-start.json`、`collected.json`、JUnit、日志和 `acceptance-complete.json`，状态为 passed 且退出码为零。RSS 还生成测量前后协议清单、四组原始样本和汇总。性能使用 Agent 的 release harness 与 `scripts/browser-d1-report.py`，报告与功能测试分开。新场景实现时扩展收集入口并增加其自身的校验测试，不能靠手工挑选少量用例称作完整阶段验收。

### 13.1 Agent 原生与可控测试

Agent 常规检查和真实 v1 命令见[维护指南](maintenance.md)。共同语义原生测试需指定 `RDH_BROWSER_EXECUTABLE`、`RDH_FIREFOX_EXECUTABLE`、同源码构建的 `RDH_BIDI_HELPER` 和新的私有 `RDH_D3_EVIDENCE`；Firefox 隔离/监督测试另用 `RDH_D2B_EVIDENCE`，直接回环探针用 `RDH_D2A_EVIDENCE`，`RDH_FIREFOX_VERSION` 与固定浏览器版本一致。这些名称是现有测试接口，保留以便执行，不表示需要另建阶段文档。探针的主机回环监听只验证其边界，不能作为产品 namespace 隔离证据。

在支持所需 Linux namespace/pidfd 的一次性环境中运行，使用已核对摘要的浏览器。跨用户和受限 shell 场景还需要测试用 bubblewrap 与 `sudo -n -u nobody`；这些不成为用户运行时依赖。不要通过修改宿主隔离策略把不可用环境记作可用。

### 13.2 证据与失败处理

每项 EX 记录预期/实际、通过/失败/拒绝/未运行状态、源码与产物摘要、fixture 版本、请求和输入计数、资源峰值、清理结果及证据路径。公开报告只保留合成数据；失败上下文中的临时凭据在导出时脱敏，记录原文件与导出文件摘要，原始证据在私有位置保留。

校验器须检查：收集 ID 与 JUnit 完全对应，二进制和协议前后未变，样本顺序/数量完整，重算结果与汇总一致；缓存计数、原生租约、pending、任务、进程和目录分别核对。总体通过数不能掩盖某个未运行的平台、客户端或扩展。

发生失败时保存第一次失败及可复现条件，定位到身份、授权、准入、原生执行、结果披露或清理中的具体边界；修复使用独立提交并重跑受影响路径，再判断是否需要完整矩阵。测量环境漂移记 `not_run` 并建立新一轮证据，不能改门槛或删除失败样本。

出现旧引用重新生效、输入重放、主体/控制越界、敏感内容泄露、核心事件丢失后继续输入、未结算工作提前释放、未知清理伪报成功，立即停止该能力放行。收益不足只阻止相应优化公开，不削弱原完整观察功能。
