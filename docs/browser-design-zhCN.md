# 面向 AI 的浏览器架构与实现路线

AI 应能在一次会话中找到目标、执行操作、解释失败，并用网页上的业务结果核对任务。建议先交付一个能解释“点击提交后发生了什么”的完整流程，再按真实任务的缺口补充页面动作和 DevTools 能力。密码、验证码和必须由本人完成的验证通过现有人工页面处理。已实现的工具、平台、资源上限与回退方法见[浏览器实现与维护](browser-implementation-zhCN.md)。

## 从一次提交定义工具分工

例如，用户要求修改表格中一条记录。AI 从观察结果确认记录及其编辑按钮，填写字段，提交一次，然后重新查找**同一条记录**。如果记录没变，可能是控件被遮挡、表单在本地拒绝、脚本异常、请求失败，或服务端已更新而页面还没刷新。仅凭“按钮已点击”无法选择下一步。

| 可判定的现象 | AI 的下一步 | 判定依据 |
| --- | --- | --- |
| 引用过期，或当前 ref 的 `browser_inspect` 显示被遮挡 | 重新观察这条记录，用 DOM/局部布局证据定位挡住它的元素。按任务语义关闭非敏感提示或滚动，再取得新引用 | 新目标属于原记录，动作前重新检查命中条件 |
| 页面显示字段错误，尚未请求服务端 | 读字段和可见错误，在已有授权与输入范围内修改，再核对页面 | 改正后错误消失，目标记录显示预期值 |
| 点击后页面无变化，或返回 HTTP 200 却显示失败 | 读取同一动作时间窗内的异常、请求结果和页面错误。无从判别时保留可能原因 | 页面数据或业务确认能够定位到原记录。请求状态只作为辅助证据 |
| 请求或输入的结果为 `unknown` | 按原 `operation_id` 查回执、会话和 tab，等相关输入结算，恢复后读取原记录 | 观察到预期业务状态，或明确报告仍未验证。写请求不自动重放 |
| 站点要求本人验证或敏感输入 | 暂停并将 `human_url` 交给用户。交回后取得新代次，重新定位原任务 | 用户明确交回并允许披露，AI 只验证业务结果。文件选择使用独立批准页 |

现有工具能看到控件遮挡和页面上的字段错误。要判断是否发过请求，还需采集覆盖了整个动作的网络事件，且不能有缺口。当前采集窗口能记录网络响应和传输失败，Firefox 还能记录控制台等级与未捕获异常。后台请求也会出现在窗口中，事件与动作的因果关系需要另行核对。耗时归因仍在规划中。若采集在动作之后才开启，应标明此前时段未观测，并从现有页面和回执继续判断。

## 模块职责与数据边界

| 模块 | 建议的实现位置与责任 |
| --- | --- |
| AI 客户端 | 先读工具 schema 和设备/会话能力。保留当前任务、目标记录及预期结果，决定下一步。根据 `coverage` 处理没读全的页面，只在有 reducer 的客户端协商增量。用户交还后重新发现状态 |
| Core / Gate | 沿用 `apps/core/src/browser`、`mcp_tools.rs` 和现有 MCP 契约。Core 核对主体、连接、实际能力、计量和最终披露，验证输出形状及完整消息字节。Gate 更新内嵌目录。`browser_guidance` 根据能力给出可执行示例 |
| Agent 会话运行时 | 在 `runtime/v2` 中持有观察、动作、控制代次与采集窗口。每项能力标明作用域、是否有页面副作用、绝对期限和清理责任。控制变更阻止旧输入入队及旧内容交付 |
| 页面语义与原生 adapter | `semantic::Page` 保留跨引擎共用的记录、引用、动作条件与覆盖语义。CDP/BiDi 分别实现类型化的读取和动作，拥有原生对象、事件、流及待决命令。用独立扩展声明引擎特有能力 |
| Business 人工页面 | 在已有会话中提供明确接管、受保护输入、交还及披露确认。独立文件批准只授权一个文件给指定站点。网页处理用户输入，AI 继续负责任务和验收 |

原生方法和调试端点留在设备内。每个公开扩展都从一个具体任务定义输入、可观察结果、失败状态和预算。各种标识各有用途。动作 `ref` 用于输入，`node_id` 用于查读节点，事件序号与 capture_id 一起定位采集窗口内的一条记录。页面文字、错误消息和站点日志都属于不受信任的数据。敏感字段要在设备端进入缓冲区前处理，并在 Core 交付时重新核对权限。

## 功能交付顺序

下表是建议的交付顺序。每一项都能经公开 MCP 和合成页面独立验收。`native_ax` 的实现状态与适用后端见[维护说明](browser-implementation-zhCN.md#可用的诊断与增量展示)。

| 顺序 | 交付内容 | 可以进入下一步的证据 |
| --- | --- | --- |
| 1. 确定操作基线 | 固定双后端观察、`inspect`、DOM/局部布局、控制权和回执的共同语料。用 CDP 单节点原生无障碍（AX）用例复核对象回收和撤权后的披露。首个样例覆盖重复行、节点替换、遮挡和输入后结果不明 | 同名行不会被误操作，替换节点后旧 ref 失效，诊断不改变输入计数，响应丢失时网站只收到一次提交 |
| 2. 解释一次失败 | 用已实现的 `task_events` 开窗，按序号读取类别与状态，对未发出请求的原生表单，用 `read_validation` 查看目标字段的约束原因，再核对同一记录的业务结果。下一步按失败样例补齐两种后端的诊断覆盖 | AI 可区分本地校验失败、脚本异常、请求失败、HTTP 成功但业务拒绝，或明确指出证据不足。普通故障无需人工接管 |
| 3. 扩大可操作页面范围 | 已支持容器定向滚动和对控件引用的原生悬停。下一步使用虚拟列表、组合控件与有明确起终点的拖放样例补足动作。复用 ref、frame 身份、命中检查和最后提交门。配套增加按目标状态或记录等待的条件 | AI 能独立操作菜单、虚拟列表和 iframe 中的目标。遮罩、页面缩放、目标移动或控制换代后，过期输入被拒绝。动作成功以目标记录的变化判定 |
| 4. 按问题深入诊断 | 根据前两阶段的问题频率，增加匹配 CSS 规则和有限的性能采样。为脚本错误提供有限栈位置，为网络错误提供失败阶段和重定向关系。每种细查单独协商 | 能从“不可见”追到负责的规则，或从“长时间无响应”定位到任务/请求区间。未采集、来源不可判定都保留在结果中 |
| 5. 验证真实使用范围 | 在目标 AI 客户端验证工具发现、图片呈现、长任务续接、人工交还、文件批准与错误恢复。按 OS、CPU、浏览器产品/版本和客户端分别登记实测结果，再决定默认开启哪些扩展 | 同一任务从建立会话到核对业务结果可重复完成，回退后旧客户端仍可完整观察。性能、关闭清理与披露门槛同时通过 |

对于 canvas、自绘控件或 closed shadow，先支持用截图获取可见上下文。确有任务需要指针操作时，单独设计绑定截图帧、tab、文档代次、视口和 DPR 的定位凭据，限定作用区域并在派发前重新核实。无法识别目标或排除敏感区域时返回覆盖缺口。这个能力应在已有语义动作无法解决的具体样例上评估。

## 单节点原生无障碍证据

Agent 通过 CDP 读取单节点原生 AX，Core 校验返回内容，Server 的 `native-ax` 验收阶段覆盖公开 MCP 调用。字段与资源边界见[实现说明](browser-implementation-zhCN.md#单节点原生无障碍证据)。对同一批合成页面核对原生角色和状态、隐藏节点、DOM/AX 名称不一致及敏感值。深度与数量上限分别构造输入，避免由另一项预算提前截断而误判覆盖。

回归时覆盖多节点响应被拒绝、取消或超时后的包装对象仍归属原连接、释放成功或原生 session 退出后结算、v1/BiDi 拒绝、主体或代次变化停止披露，以及原动作 ref 和增量基线仍然有效。真实浏览器和公开 MCP 各自留下证据。[原生 AX 用例](../src/browser/runtime/v2/accessibility_native_tests.rs) · [合成页面和 oracle](../tests/fixtures/native-ax-v1)

## 第一版 DevTools 诊断接口

已提供 `task_events` 版本 1。AI 可以围绕一次已授权动作开窗、读取和停止；窗口与输入各有自己的操作回执。事件流保存来自浏览器的固定类别和状态码。操作系统、浏览器与客户端组合的放行仍独立验收。字段、能力协商、分页和回收规则见[实现说明](browser-implementation-zhCN.md#动作期间的事件)。

下一步由失败用例决定补哪些事实。Chromium 的控制台订阅会出现带原生对象的消息。先证明旧消息不会回放、对象配额与释放可结算、日志洪峰不会阻塞导航和人工接管，再向 CDP 会话声明 `console`。网络时间窗也可能包含页面后台请求；跨重定向识别、失败阶段和有限的脚本栈位置需要独立定义来源与覆盖范围。两种后端都应保持普通输入回执和诊断内容分离，优先用目标记录判断网站业务结果。

样式诊断从单个证据节点开始。先用 `read_layout` 查看计算值和遮挡，再为 CDP 单独协商匹配规则读取。Agent 应验证同一 frame 和文档的节点绑定，负责 DOM/CSS domain 的启停、临时节点和取消后的清理。首批样例覆盖 `display`、`visibility`、`pointer-events` 及 `!important`。返回筛选后的属性、规则来源类别与覆盖范围；无法证明层叠胜者时标明原因未知。验收应包含外部样式表、导航、迟到回包和人工接管。

性能先给任务耗时、长任务与资源阶段摘要，需要进一步定位时再提供有期限的 trace 私有制品和受限查询。将来若提供 VM 暂停、步进等会改变页面执行的能力，须与普通输入互斥，并证明超时或断连后能恢复执行。Agent 的控制暂停和 JavaScript VM 暂停分别记录状态。[CDP CSS](https://chromedevtools.github.io/devtools-protocol/tot/CSS/)

## 人工接管与续接

普通校验错误、脚本异常、请求失败和加载缓慢由 AI 在当前权限范围内处理。缺少证据时，AI 应告诉调用者哪个步骤未验证、已知事实是什么、还可检查什么。敏感输入或站点要求本人验证时，使用原有 `human_url`，由用户在已认证页面取得控制。站点要求硬件安全密钥或其他系统级 UI 且远程视口无法承载时，明确说明该验证方式的限制。

交给人工前，客户端保存原任务、目标记录、已提交操作 ID 和待验证条件。保存内容只含恢复任务所需的信息。用户在页面上输入秘密、验证身份，检查可披露的页面内容后明确交还。租约到期继续保持披露限制。AI 回到原会话后先查控制者和新代次，再观察并核对结果。已结束的对话目前需要用户返回并发送“继续”。将来可由客户端订阅仅含会话状态的交还通知，收到后仍从工具重新获取授权状态。文件选择与批准沿用 `files_url` 的一次性授权。

## 验收入口与放行条件

| 要回答的问题 | 可执行入口与断言 |
| --- | --- |
| 两个引擎是否操作了同一业务目标？ | [共同语义测试](../src/browser/semantic/tests)、[固定页面及 oracle](../tests/fixtures/semantic-dom-v1)。覆盖同名记录、open shadow、跨 frame、同 URL reload、BFCache、节点替换及引用失效。在公开 MCP 上核对网站接收的输入次数 |
| 执行、撤权和清理是否正确？ | [CDP 传输测试](../src/browser/engine/cdp/wire)、[BiDi 传输测试](../src/browser/engine/bidi/wire/tests)。在入队前、入队后、超时及迟到回包时切换控制。另一个 tab 能继续工作，关键事件缺失会阻止新输入，未结算对象/流仍有所有者 |
| 拦截发生在哪个阶段？ | [导航测试](../src/browser/semantic/tests/navigation.rs) 中 BC-30 检查新上下文的首个文档请求与重定向。BC-31 区分 DNS 检查、实际连接地址证据与严格策略，分别记录连接次数和 HTTP 请求次数 |
| 人工边界能否维持？ | Server `tests/core/test_browser_human.py`、`test_browser_file_approval.py`、`test_browser_guidance_races.py`。用合成秘密验证接管窗口内 AI 的读写、截图与诊断均被拒绝，交还前不交付旧读取。文件批准路径保持 AI 控制和一次使用，普通报错无需接管 |
| 新诊断是否帮助 AI 作出正确判断？ | 为遮挡、JS 异常、HTTP 失败、HTTP 200 业务拒绝、响应丢失、本人验证分别固定页面终态和提交计数。记录任务完成率、误报成功率、普通故障人工接管数、诊断调用数/字节数。纳入事件洪峰、跨主体、换代与双后端能力不对称。普通任务与必须本人验证的任务分别计数。基准语料中重复提交、敏感内容披露和无证据宣称成功均为阻断项 |
| 增量与新能力能否独立关闭？ | Server `clients/browser-observation-delta.test.mjs`、`tests/core/test_browser_observation_delta.py`。用同一次采集的完整观察验证重建。稀疏组实际 MCP 总字节不超过始终 full 的 70%。覆盖未知扩展、旧客户端、重连、乱序及基线淘汰 |
| 真实调用链是否通过？ | Server `scripts/run_browser_acceptance.py` 从公开 MCP 驱动 Gate/Core、Agent 及真实浏览器。根据改动选择 `contracts`、`v1`、`v2`、`evidence`、`capture`、`form-validation`、`scoped-scroll`、`hover`、`file-approval`、`delta-corpus`、`budgets`、`recovery`、`linux-tls` 或 `rss`。以脚本的 `--help` 为准。执行需要专用 PostgreSQL、配套产物和浏览器。同一 PostgreSQL 实例的阶段串行。收集清单须与 JUnit 一致，并保留首次失败 |

在 Server 根目录核对 `python3 scripts/run_browser_acceptance.py --help`。例如，在准备好专用测试环境后运行下面的 DOM 证据阶段。`RDH_ACCEPT_ENV` 指向包含配套测试产物与数据库设置的私有 JSON，`RDH_ACCEPT_OUT` 指向一个尚不存在的输出目录。成功时退出码为 0，目录中的 `acceptance-complete.json` 记录通过状态。

```sh
python3 scripts/run_browser_acceptance.py --phase evidence \
  --env-json "$RDH_ACCEPT_ENV" --output "$RDH_ACCEPT_OUT"
```

性能门槛沿用同机同 release profile 的配对测量。CDP 耗时每批 p50 增量不超过 `max(10%, 5 ms)`、p95 不超过 `max(15%, 10 ms)`，协议往返 p95 不超过基线 120%。控制换代在满载下 1,000 次的 p99 不超过 100 ms。Linux x86_64 GNU 的 Firefox 在 2 CPU/4 GiB 固定页面上冷启动 p95 ≤ 10 秒、单段观察 ≤ 3 秒、稳定输入确认 ≤ 1 秒（均为 p95）。剥离后 Agent 二进制增量 ≤ `max(15%, 2 MiB)`，不增加外部浏览器驱动依赖。

延迟测量至少三个交替批次，每批预热 20 次再采 100 次。固定 CDP 对照为 `06e43b18763292a89fe79f2df1992e4053225ff2`，汇总入口为 [browser-d1-report.py](../scripts/browser-d1-report.py)。RSS 以 v1、v2/CDP、v2/BiDi、v1 四组依序测量，每组预热 20 次、采样 100 次。Agent 和浏览器各自增长 ≤ 16 MiB，新后端空闲开销 ≤ 8 MiB，两个 v1 空闲基线相差超过 8 MiB 时需重新测量。Server `scripts/summarize_browser_rss.py` 对四组原始样本重算。客户端、平台或浏览器版本的放行需要该组合的实测。
