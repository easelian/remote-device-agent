# 面向 AI 的浏览器架构与实现路线

AI 应能在一次会话中找到目标、执行操作、解释失败，并用网页上的业务结果核对任务。页面操作和 DevTools 能力围绕实际任务组织，例如解释“点击提交后发生了什么”，再核对原记录。密码、验证码和必须由本人完成的验证通过现有人工页面处理。已实现的工具、平台、资源上限与回退方法见[浏览器实现与维护](browser-implementation-zhCN.md)。

## 从一次提交定义工具分工

例如，用户要求修改表格中一条记录。AI 从观察结果确认记录及其编辑按钮，填写字段，提交一次，然后重新查找**同一条记录**。如果记录没变，可能是控件被遮挡、表单在本地拒绝、脚本异常、请求失败，或服务端已更新而页面还没刷新。仅凭“按钮已点击”无法选择下一步。遇到嵌套记录，要分别核对父订单和子订单。查找按钮、采样该记录的结果时都应跳过内嵌记录。动作引用另行保留外层记录的身份与内容，用于检查页面是否把子记录移到了别的订单。

| 可判定的现象 | AI 的下一步 | 判定依据 |
| --- | --- | --- |
| 引用过期，或当前 ref 的 `browser_inspect` 显示被遮挡 | 重新观察这条记录，用 DOM/局部布局证据定位挡住它的元素。按任务语义关闭非敏感提示或滚动，再取得新引用 | 新目标属于原记录，动作前重新检查命中条件 |
| 页面显示字段错误，目标记录未更新 | 先保存原字段的原生校验原因或页面提示，再使用已授权的输入修正 | 浏览器报告的字段约束和站点拒绝分别取证，提交后重新读取原记录的状态 |
| 点击后页面无变化，或返回 HTTP 200 却显示失败 | 读取同一动作时间窗内的异常、请求结果和页面错误。无从判别时保留可能原因 | 页面数据或业务确认能够定位到原记录。请求状态只作为辅助证据 |
| 请求或输入的结果为 `unknown` | 按原 `operation_id` 查回执、会话和 tab，等相关输入结算，恢复后读取原记录 | 观察到预期业务状态，或明确报告仍未验证。写请求不自动重放 |
| 站点要求本人验证或敏感输入 | 暂停并将 `human_url` 交给用户。交回后取得新代次，重新定位原任务 | 用户明确交回并允许披露，AI 只验证业务结果。文件选择使用独立批准页 |

遇到提交无响应时，先检查控件遮挡和页面上的字段错误。Chromium 和 Firefox 的采集窗口都能记录顶层页面的控制台级别、脚本异常和网络结果。客户端在动作前按会话声明的类别开窗。普通网络事件记录响应和传输失败。会话另有 `network_progress` 时，客户端可在开窗时启用请求跟踪，检查哪些请求已开始、哪些仍在等待响应头。后台请求也会出现在窗口中，提交结果仍须从原记录核对。开窗晚于动作时，应明确此前时段缺少证据。

排查“点击成功、订单仍待审批”时，可用同一浏览器版本、同一合成页面和独立订单副本做对照。先记录订单号和初始状态，再各提交一次。MCP 客户端读取 `read_requests`、控制台事件和原订单状态。`agent-browser` 可用 `network requests`、`console --json` 和页面快照核对；`errors` 查看未处理的页面错误，站点主动调用 `console.error` 时应查 `console`。最后核对站点收到的提交次数。一次 POST 返回 HTTP 200、控制台报错、页面仍显示待审批时，可以确认请求已收到响应。若页面没有新的业务凭据，记录审批结果尚未确认，保留原操作回执，避免再次提交。

## 模块职责与数据边界

| 模块 | 建议的实现位置与责任 |
| --- | --- |
| AI 客户端 | 先读工具 schema 和设备/会话能力。保留当前任务、目标记录及预期结果，决定下一步。根据 `coverage` 处理没读全的页面，只在有 reducer 的客户端协商增量。用户交还后重新发现状态 |
| Core / Gate | 沿用 `apps/core/src/browser`、`mcp_tools.rs` 和现有 MCP 契约。Core 核对主体、连接、实际能力、计量和最终披露，验证输出形状及完整消息字节。Gate 更新内嵌目录。`browser_guidance` 根据能力给出可执行示例 |
| Agent 会话运行时 | 在 `runtime/v2` 中持有观察、动作、控制代次与采集窗口。每项能力标明作用域、是否有页面副作用、绝对期限和清理责任。控制变更阻止旧输入入队及旧内容交付 |
| 页面语义与原生 adapter | `semantic::Page` 保留跨引擎共用的记录、引用、动作条件与覆盖语义。CDP/BiDi 分别实现类型化的读取和动作，拥有原生对象、事件、流及待决命令。用独立扩展声明引擎特有能力 |
| Business 人工页面 | 在已有会话中提供明确接管、受保护输入、交还及披露确认。独立文件批准只授权一个文件给指定站点。网页处理用户输入，AI 继续负责任务和验收 |

原生方法和调试端点留在设备内。每个公开扩展都从一个具体任务定义输入、可观察结果、失败状态和预算。各种标识各有用途。动作 `ref` 用于输入，`node_id` 用于查读节点，事件序号与 capture_id 一起定位采集窗口内的一条记录。页面文字、错误消息和站点日志都属于不受信任的数据。敏感字段要在设备端进入缓冲区前处理，并在 Core 交付时重新核对权限。

## 功能交付顺序

下表是建议的交付顺序。每一项都能经公开 MCP 和合成页面独立验收。`native_ax` 的实现状态与适用后端见[维护说明](browser-implementation-zhCN.md#可用的诊断与增量展示)。

| 顺序 | 交付内容 | 可以进入下一步的证据 |
| --- | --- | --- |
| 1. 确定操作基线 | 固定双后端观察、`inspect`、DOM/局部布局、控制权和回执的共同语料。用 CDP 单节点原生无障碍（AX）用例复核对象回收和撤权后的披露。首个样例覆盖重复行、节点替换、遮挡和输入后结果不明 | 同名行不会被误操作，替换节点后旧 ref 失效，诊断不改变输入计数，响应丢失时网站只收到一次提交 |
| 2. 解释一次失败 | 用已实现的 `task_events` 开窗，按序号读取类别与状态，对提交后仍显示字段错误的原生表单，用 `read_validation` 查看目标字段的约束原因，再核对同一记录的业务结果。若提交后没有响应，启用请求跟踪可区分已观察到开始的请求与已有响应头的请求 | AI 可区分本地校验失败、脚本异常、请求失败、HTTP 成功但业务拒绝，或明确指出证据不足。普通故障无需人工接管 |
| 3. 扩大可操作页面范围 | 已支持原生悬停、定向滚动、通过 ARIA 位置区分虚拟列表的同名选项，并可在指定业务记录上等待结果。Chromium 可在同一主文档的视口内拖放已识别的两端，接管或端点失效时取消拖动。下一步在 Firefox 验证正常投放、中途取消和会话恢复，再评估跨 frame 与拖动中滚动 | AI 能独立操作菜单、虚拟列表和 iframe 中的目标。遮罩、页面缩放、目标移动或控制换代后，过期输入被拒绝。动作成功以目标记录的变化判定 |
| 4. 按问题深入诊断 | 已提供 CDP 单节点匹配样式诊断，两个后端均可关联请求开始、响应、传输失败和重定向。异常可按事件序号读取前三个同步栈帧的位置。下一步用仍无法解释的页面评估是否需要异步调用关系或更细的连接失败阶段，每种细查单独协商 | 能从“不可见”追到负责的规则，或从“长时间无响应”定位到任务/请求区间。未采集、来源不可判定都保留在结果中 |
| 5. 验证真实使用范围 | 在目标 AI 客户端验证工具发现、图片呈现、长任务续接、人工交还、文件批准与错误恢复。按 OS、CPU、浏览器产品/版本和客户端分别登记实测结果，再决定默认开启哪些扩展 | 同一任务从建立会话到核对业务结果可重复完成，回退后旧客户端仍可完整观察。性能、关闭清理与披露门槛同时通过 |

### 同一主文档内的拖放

第一版以看板为验收任务。客户端从同一次主文档观察中选定源卡片和接收列，Agent 用两端的身份、所属记录、命中位置和控制代次约束原生输入。CDP 实现将正常放下与故障取消分开，正常放下一直受控制代次约束。执行状态为 `unknown` 时，客户端按原操作回执追踪，恢复后重新读取卡片所属列。维护文档给出了[拖放参数与回退方法](browser-implementation-zhCN.md#用拖放移动看板卡片)和[独立验证页面行为的步骤](browser-implementation-zhCN.md#独立验证页面行为)。

Linux 上的 Firefox 160 保留 `ref_drag.available: false`。随包 `omni.ja` 的 `shared/webdriver/Actions.sys.mjs` 将指针释放交给 `synthesizeMouseAtPoint`。默认输入路径进入 `external/EventUtils.js` 的 `_maybeEndDragSession` 时会结束已有拖动，源码在此标记投放事件尚待实现。真实看板在默认配置下收到 `dragstart` 和目标的 `dragover`，没有收到 `drop`。开启异步鼠标派发也未产生业务写入。同一有窗口 Firefox 用 X11 鼠标拖动后，正确卡片换列，站点写入一次。

验证新版本或新输入路径时，先证明正常拖动能在同一看板写入一次。再在指针进入接收列后发起接管，核对取消产生零次写入，并用原会话的新观察完成下一次操作。只有通过这两项验证，候选和会话才应声明支持拖放。

跨 frame 与自动滚动会改变坐标和命中目标，应在分别完成文档归属、滚动后两端重新定位及取消测试后，再发布独立的能力声明。

Canvas 和 closed shadow 的指针输入依赖当前截图。Agent 绑定一次性的图像标识、文档、视口和控制代次，在派发前复核像素和目标。视觉手势的验收页面同时放置目标与邻单，直接核对网站写入。表单错误优先从浏览器实际发出的原生校验事件取得，再检查原记录。后续可用持续动画和复杂嵌套视口测量保守拒绝率，作为缩小复核区域的依据。[现行实现与边界](browser-implementation-zhCN.md)

## 单节点原生无障碍证据

Agent 通过 CDP 读取单节点原生 AX，Core 校验返回内容，Server 的 `native-ax` 验收阶段覆盖公开 MCP 调用。字段与资源边界见[实现说明](browser-implementation-zhCN.md#单节点原生无障碍证据)。对同一批合成页面核对原生角色和状态、隐藏节点、DOM/AX 名称不一致及敏感值。深度与数量上限分别构造输入，避免由另一项预算提前截断而误判覆盖。

回归时覆盖多节点响应被拒绝、取消或超时后的包装对象仍归属原连接、释放成功或原生 session 退出后结算、v1/BiDi 拒绝、主体或代次变化停止披露，以及原动作 ref 和增量基线仍然有效。真实浏览器和公开 MCP 各自留下证据。[原生 AX 用例](../src/browser/runtime/v2/accessibility_native_tests.rs) · [合成页面和 oracle](../tests/fixtures/native-ax-v1)

## 第一版 DevTools 诊断接口

已提供 `task_events` 版本 1。AI 可以围绕一次已授权动作开窗、读取和停止；窗口与输入各有自己的操作回执。事件流保存来自浏览器的固定类别和状态码。操作系统、浏览器与客户端组合的放行仍独立验收。字段、能力协商、分页和回收规则见[实现说明](browser-implementation-zhCN.md#动作期间的事件)。

当会话声明 `console` 和 `network` 时，AI 可以在一次操作后同时检查顶层页面的脚本异常、控制台级别和网络结果。Chromium 的临时诊断会话和页面控制会话附着到同一目标。诊断会话只订阅当前窗口需要的 Runtime 事件，控制会话继续处理输入、导航和人工接管。Firefox 使用 BiDi 的日志和网络订阅。旧客户端和旧 Agent 按各自公布的类别协商。

Chromium 会在启用 Runtime 时回放历史记录。Agent 等待启用确认，检查事件原始时间与顶层文档的默认执行环境，只把当前控制代次内的新事实交给 AI。窗口或文档失效后释放诊断会话。需要区分保存逻辑内部抛错还是调用者出错时，可显式协商 `exception_locations` 查看有界位置。分别检查调用者和首帧的窗口内来源编号，再结合网络证据和原订单状态判断。验收时仍须对照一次操作的提交次数、目标记录终态及获准披露的时间范围。

### 诊断仍在等待响应的请求

例如，网站已经收到保存订单的 POST，但尚未发送响应头。此时两个后端的 `read_events` 都可能返回空列表，`dropped_count` 也可以是 0。若提交前已开启请求跟踪，`read_requests` 可以看到尚未收到响应头的 POST。AI 应保留原操作 ID，等待或只读核对订单，避免再次提交。

请求进度由可协商的 `network_progress` 扩展提供。客户端显式启用后，Agent 将浏览器报告的请求开始、响应或失败关联到本窗口的短标识。该标识只在原 tab、文档和控制代次有效。窗口内只看到开始时，客户端可报告“尚未观察到结果”。开始或结果落在窗外、记录已淘汰、发生重定向而链路不完整时，应返回缺少哪段证据。每个窗口最多保留 32 条请求记录。请求地址、表单值、头部及原生标识留在设备内。沿用当前 `network` 类别的客户端继续收到已有的响应和失败摘要。

验收页面将目标写请求和后台请求同时挂起，分别放行响应，并通过站点记录核对每次提交。测试须覆盖开窗前已开始的请求、诊断中途交给人工、重定向以及事件淘汰。请求与响应的关联只能解释传输进度。某个请求是否由这次点击触发、业务结果是否生效，仍需页面证据。

AI 排查点击失败时，先用 `browser_inspect` 检查命中，再用 `find_nodes` 定位页面元素。对同一个 `node_id`，`read_layout` 返回计算值，`read_styles` 返回目标本身的声明，CDP 的 `read_ancestor_styles` 可以补查普通父链上的 `pointer-events` 或 `visibility` 声明。

例如，同一容器里的两个按钮都能查到祖先的 `pointer-events: none`。第一个按钮自身没有声明，计算值为 `none`，命中测试失败。第二个按钮有行内 `auto`，计算值为 `auto`，命中测试通过。AI 应结合这三项证据决定能否操作，再按业务记录验证结果。CSS 变量和完整层叠顺序仍未解析，`cascade` 保持 `undetermined`。[样式诊断用法](browser-implementation-zhCN.md#定位影响控件的样式)

查询必须使用同一节点的原始 `node_id`，不能用相邻节点、重挂后的新节点或名称相同的节点替代。Agent 在目标所属文档内最多检查四层普通父节点。节点重挂使正在采集的结果失效，遇到 shadow root 或 slot 边界时返回不支持。一次祖先查询合计最多检查 32 条规则、128 项属性，返回 16 项候选。敏感节点或敏感祖先零披露；不会返回页面文字、选择器、原生标识或敏感 CSS 声明。直接样式读取在 ancestor 查询不可用时仍独立有效。

按下文[验收示例](#验收入口与放行条件)在 Server 根目录运行，将阶段改为 `ancestor-styles`，可验证普通父链、直接覆盖、敏感父节点、shadow/slot 边界及节点重挂。重挂期间的采样应被拒绝，再次读取同一元素时只应看到当前父链。

遇到命中和样式结果不一致时，用同一 Chrome 可执行文件、同一测试页面，在独立的 `agent-browser` 会话中执行 `snapshot -i`、`get styles @ref` 和 `click @ref`。每个客户端使用自己观察得到的引用。样式读取期间站点写入应为 0。对照点击后，再检查页面确认文字和站点收到的写入次数；受阻按钮也可能得到 CLI 的 `clicked` 回执。

性能先给任务耗时、长任务与资源阶段摘要，需要进一步定位时再提供有期限的 trace 私有制品和受限查询。将来若提供 VM 暂停、步进等会改变页面执行的能力，须与普通输入互斥，并证明超时或断连后能恢复执行。Agent 的控制暂停和 JavaScript VM 暂停分别记录状态。[CDP CSS](https://chromedevtools.github.io/devtools-protocol/tot/CSS/)

## 人工接管与续接

普通校验错误、脚本异常、请求失败和加载缓慢由 AI 在当前权限范围内处理。缺少证据时，AI 应告诉调用者哪个步骤未验证、已知事实是什么、还可检查什么。敏感输入或站点要求本人验证时，使用原有 `human_url`，由用户在已认证页面取得控制。站点要求硬件安全密钥或其他系统级 UI 且远程视口无法承载时，明确说明该验证方式的限制。

交给人工前，客户端保存原任务、目标记录、已提交操作 ID 和待验证条件。保存内容只含恢复任务所需的信息。用户在页面上输入秘密、验证身份，检查可披露的页面内容后明确交还。租约到期继续保持披露限制。AI 回到原会话后用 `browser_tabs` 确认控制者并取得新代次，重新观察并定位原记录。例如，验证 B42 的审批结果时，即使相邻 A17 已获批，也必须在 B42 上核对状态。已结束的对话目前需要用户返回并发送“继续”。将来可由客户端订阅仅含会话状态的交还通知，收到后仍从工具重新获取授权状态。文件选择与批准沿用 `files_url` 的一次性授权。

在 Server 根目录核对 `python3 scripts/run_browser_acceptance.py --help`。例如，在准备好专用测试环境后运行下面的 DOM 证据阶段。`RDH_ACCEPT_ENV` 指向包含配套测试产物与数据库设置的私有 JSON，`RDH_ACCEPT_OUT` 指向一个尚不存在的输出目录。成功时退出码为 0，目录中的 `acceptance-complete.json` 记录通过状态。

```sh
python3 scripts/run_browser_acceptance.py --phase evidence \
  --env-json "$RDH_ACCEPT_ENV" --output "$RDH_ACCEPT_OUT"
```

性能门槛沿用同机同 release profile 的配对测量。CDP 耗时每批 p50 增量不超过 `max(10%, 5 ms)`、p95 不超过 `max(15%, 10 ms)`，协议往返 p95 不超过基线 120%。控制换代在满载下 1,000 次的 p99 不超过 100 ms。Linux x86_64 GNU 的 Firefox 在 2 CPU/4 GiB 固定页面上冷启动 p95 ≤ 10 秒、单段观察 ≤ 3 秒、稳定输入确认 ≤ 1 秒（均为 p95）。剥离后 Agent 二进制增量 ≤ `max(15%, 2 MiB)`，不增加外部浏览器驱动依赖。

延迟测量至少三个交替批次，每批预热 20 次再采 100 次。固定 CDP 对照为 `06e43b18763292a89fe79f2df1992e4053225ff2`，汇总入口为 [browser-d1-report.py](../scripts/browser-d1-report.py)。RSS 以 v1、v2/CDP、v2/BiDi、v1 四组依序测量，每组预热 20 次、采样 100 次。Agent 和浏览器各自增长 ≤ 16 MiB，新后端空闲开销 ≤ 8 MiB，两个 v1 空闲基线相差超过 8 MiB 时需重新测量。Server `scripts/summarize_browser_rss.py` 对四组原始样本重算。客户端、平台或浏览器版本的放行需要该组合的实测。

复测固定基线时，用 Cargo 的 `--config 'profile.release.lto="fat"' --config 'profile.release.package.rdh-agent.opt-level="z"' --config 'profile.release.package.rdh-agent.codegen-units=1'` 对齐构建参数。先用 `cargo build --release --bin rdh` 构建发布程序，候选版本启用 `experimental-browser-bidi`，立即保存两边的程序和 SHA-256。再用 `cargo test --release --lib --no-run` 构建原生测试程序。集成测试构建可能重新链接带开发依赖特性的 CLI。体积比较使用保留符号名的发布产物。
